# Design Decisions & Architecture Notes

Things that aren't obvious from the code alone.

## Why an Express backend instead of all-frontend?

Three reasons:
1. **NJT GTFS-RT is protobuf** — browsers can't easily parse it. The server decodes protobuf and returns JSON.
2. **NJT requires auth tokens** — the server caches the 24h token and keeps credentials out of the browser.
3. **CORS** — PANYNJ, NWS, Connexionz, and MTA APIs don't have CORS headers. The server proxies everything.

In production on a Pi, the Express server replaces the Vite proxy entirely — it serves the static build AND proxies all APIs.

## Why separate GTFS-RT feeds for MTA subway?

The MTA splits subway real-time data into 8 feeds by line group (1-7, ACE, BDFM, G, JZ, NQRW, L, SI). When querying a station like Herald Square that has both BDFM and NQRW lines, the server must check multiple feeds. Each feed is cached for 30 seconds to avoid hammering the API.

## Why static station-to-route mapping for MTA?

The live GTFS-RT feed only contains trains currently running. At night, the B train doesn't run, so it wouldn't appear in the line picker. The static mapping (from `mta_station_routes.json`, built from GTFS stops.txt) ensures all lines that *ever* serve a station are shown, regardless of time of day.

The mapping file is generated by `server/build_station_routes.mjs` and cached in `.cache/`. It maps each station's parent stop ID to all route IDs that serve it, built from `stop_times.txt` + `trips.txt` + `routes.txt`. The server auto-builds it on startup if missing.

## Why consolidated stations in the subway picker?

MTA has multiple stop IDs for the same station name (e.g. Herald Square has D17 for BDFM platforms and R17 for NQRW platforms). The station search consolidates these by name so the user sees one "34 St-Herald Sq" entry instead of two. The consolidated station stores all IDs, and the query endpoint checks all of them.

## Why the NJT bus schedule loads ALL 16,820 stops?

Originally we only loaded stops for preconfigured cards. But when we added the dynamic stop picker ("Other routes…"), any of the 273 NJT bus routes could be selected. Loading all stops at startup (~10 seconds) means any stop query returns instantly with schedule fallback data, even if the real-time feed doesn't have that bus yet.

## Why tunnel alerts have a configurable inline expiry?

PANYNJ alerts persist all day — a 6 AM lane closure alert still shows at 3 PM even though it's long resolved. The inline expiry (default 60 min) hides stale alerts from the tunnel card while keeping them in the scrolling ticker. The user can adjust this in Settings → Display.

## Why the ferry uses Connexionz instead of GTFS?

NY Waterway doesn't publish a GTFS-RT feed. Their real-time data comes from Connexionz (etacloud.connexionz.net), which powers their departure screens. The API key (`EFD912BD775313FED5D8791D11365`) is embedded in their public SPA — it's not a secret. The `eta` field is real-time minutes when a vessel is tracked; `scheduledMin` is the fallback.

## Why PATH uses a community GTFS-RT feed?

The Port Authority doesn't publish an official GTFS-RT feed for PATH. The community feed at `path.transitdata.nyc` (maintained by jamespfennell on GitHub) converts the RidePATH app data into GTFS-RT format. It's updated every 5 seconds and uses stop/route IDs compatible with the official PANYNJ GTFS static data.

Each PATH "trip" in the feed has only ONE stop time update (the next arrival at one station), not the full trip sequence. This is a limitation of the source data — PATH doesn't expose which train is which across stations. Because of this, the server matches trains by route ID + direction ID only (not by stop ID), and uses the earliest reported time as the ETA.

## Weekend/holiday PATH service uses route ID 1024

On weekends and holidays, PATH runs a modified service where JSQ-33 operates via Hoboken (replacing both HOB-33 and the standard JSQ-33). This service appears in the GTFS-RT feed as route ID `1024` rather than `861`. Route `862` (HOB-33) continues to run on weekends. The server recognizes `1024` as "JSQ-33 (weekend)" and includes it in all relevant station route lists and direction configs.

## Why PABT gate info is hardcoded?

There's no API for Port Authority Bus Terminal gate assignments. The data comes from portauthoritygate.com (last updated June 2024) and dougandadrienne.info. Gates change by time of day (day/late/overnight) but the assignments themselves rarely change. The gate schedule is stored in the server's `DIRECTIONS.inbound.busStops` config and in the frontend fallback objects.

## Why the settings panel uses draft state?

The settings panel works on draft copies of all settings. Changes only take effect when you click "Save Changes". Closing without saving reverts everything. This prevents the dashboard from flickering or breaking while you're mid-edit. The drafts are reset from the committed state every time the panel opens.

## Stop ID conventions

Different transit systems use different ID formats. The frontend uses a prefix convention to route cards to the right component:

| Prefix | Component | Example |
|---|---|---|
| `clinton`, `willow`, etc. | Preconfigured BusStopCard | `clinton` |
| `pabt_*` | Preconfigured BusStopCard (inbound) | `pabt_washington` |
| `bus:*` | DynamicBusCard (new format) | `bus:16012:125` |
| `ferry_*` | Preconfigured FerryCard | `ferry_hob14` |
| `path_*` | Preconfigured PathCard | `path_hob33` |
| `ferry:*` | DynamicFerryCard | `ferry:10:19:Midtown` |
| `path:*` | DynamicPathCard | `path:862:1:26727` |
| `mta:*` | DynamicMtaCard | `mta:D17,R17:S:B,D,F,N,Q,R,W` |
| (numeric) | DynamicBusCard (legacy) | `7935` |

The `bus:` format encodes: `bus:{gtfs_stop_id}:{selected_routes}`
The `mta:` format encodes: `mta:{station_ids}:{direction}:{selected_lines}`

## Why PABT gate lookup uses route number, not headsign

PABT gate assignments are keyed by route number (from portauthoritygate.com). Some routes like 126 have sub-variants with different gates (126 Washington → Gate 213, 126 Willow → Gate 214). The current implementation shows the primary gate for the route, which is correct for most routes but imprecise for 126.

A headsign-based lookup would be more accurate but has downsides:
- Headsigns are messy GTFS strings ("126 HOBOKEN-PATH", "126 HAMILTON PK VIA WILLOW") that are fragile to match
- Headsigns are only available at query time (when buses are running), not at card creation time
- Would require showing the gate dynamically per-departure rather than in the card header
- Only affects route 126 (and possibly a few others) — the vast majority of routes have one gate

The preconfigured 126 cards handle this by having separate cards for Washington vs Willow, each with their own gate. For the dynamic picker, showing the primary gate is a reasonable tradeoff. This can be revisited with a hybrid route+headsign lookup if needed.

## Why PABT has multiple GTFS stop IDs

Port Authority Bus Terminal has several GTFS stop IDs (16977, 16012, 16049, 16808, 16809, 16803, 16856) representing different platforms and areas. The stop search returns 16012 as the primary "PORT AUTHORITY BUS TERMINAL" entry. The server recognizes all known PABT stop IDs for gate lookup and isPabt detection.

## Why alert filtering uses two layers

The old approach had a static list of alert sources with per-source toggles. This broke in two ways: (1) alerts for transit lines not on the dashboard still showed up, and (2) turning off all toggles didn't fully suppress alerts because the `on()` helper returned `true` for any ID not in the settings object.

The new approach uses two layers:
1. **`deriveActiveAlertSources(stops)`** — scans all dashboard cards and builds a Set of alert source IDs that should exist. If no ferry card is on the dashboard, `ferry` isn't in the set.
2. **User toggles** — per-source on/off overrides. An alert only shows if its source is in the active set AND the user hasn't toggled it off.

The settings panel auto-generates toggle buttons from the active set, so adding a bus 165 card automatically creates a "Bus 165" toggle.

## Why the bus picker uses stop-first search instead of route-first

The original bus picker flow was Route → Stop, which required picking a route before seeing stops. This was awkward because: (1) you had to pick the route twice if you wanted to filter, (2) many stops serve multiple routes, and (3) it didn't match the MTA subway flow which users were already familiar with.

The new flow is Search Stop → Select Lines, mirroring the MTA subway picker. This is simpler (2 steps instead of 3), lets you see all routes at a stop before committing, and produces a card that filters to exactly the lines you want.

## Why NJT Rail uses the TrainData JSON API instead of GTFS-RT

NJT has two rail APIs at `raildata.njtransit.com`: a TrainData JSON API and a GTFS-RT protobuf API. We use the JSON API because:
- It returns richer data: station names, line colors, capacity per car, inline messages, track numbers
- The `getTrainSchedule19Rec` endpoint gives the next 19 departures with real-time status in one call
- Station alerts come embedded in the response (no separate alert fetch needed)
- No protobuf parsing required — just JSON
- Same credentials work for both APIs

The GTFS-RT API is available as a fallback if needed, but the JSON API is more practical for a dashboard.

## Why HBLR uses the bus GTFS-RT feed

HBLR (Hudson-Bergen Light Rail) is not in the NJT Rail API — it's treated as a bus route (`HBLR`) in the NJT bus GTFS-RT system at `pcsdata.njtransit.com`. This means HBLR stops appear in the bus stop search, and departures come from the same trip updates feed as buses. The `DynamicHblrCard` component filters to route `HBLR` only.

## Why PATH direction options are deduplicated

At stations served by multiple PATH lines going the same direction (e.g. Christopher St has both JSQ-33 and HOB-33 going "To 33rd St"), showing separate options for each line is confusing. The server groups by direction label and combines route IDs, so the user sees one "To 33rd St" option that queries both lines. The card then shows trains from whichever line arrives first.

## Why NJT Rail polls every 60 seconds instead of 30

The NJT Rail API has a 40,000 call/day limit. At 30-second intervals with multiple cards, you'd burn through the limit quickly. 60 seconds is a reasonable balance — rail schedules don't change as rapidly as bus GPS positions. The token is also limited to 10 refreshes/day, so we cache it for 20 hours.

## Why NYC Ferry uses GTFS-RT instead of the Connexionz ETA API

NYC Ferry's Connexionz instance provides GTFS/GTFS-RT feeds rather than the ETA JSON API that NY Waterway uses. The GTFS-RT trip updates feed gives real-time departure predictions in standard protobuf format, which we already parse for PATH and MTA subway. The GTFS static data provides station names and route colors. No API key needed.

## Why MTA Bus uses the SIRI API instead of GTFS-RT

MTA Bus real-time data is provided via the Bus Time SIRI API (bustime.mta.info), not GTFS-RT. This is a different system from the subway/rail feeds. It requires an API key and returns JSON in SIRI format with MonitoredStopVisit objects. The API also includes service alerts via SituationExchange. The route search uses the OneBusAway-compatible routes-for-agency endpoint.

## Why weather is tied to city zip codes

Originally weather had a manual toggle between Hoboken and NYC. This was confusing because the weather didn't match the direction. Now each direction has a city set by zip code, and the weather automatically shows the forecast for whichever city you're commuting from. The zip code resolves to a city name (via Zippopotam.us) and NWS grid coordinates (via api.weather.gov/points) in one step. Both the dashboard title and weather card use the resolved city name.

## Why settings use localStorage instead of a backend

Settings are user-specific and don't need to be shared or synced. localStorage is zero-infrastructure, works offline, and survives page refreshes. The key `hoboken-commuter-settings` stores a JSON snapshot of all configurable state. A "Reset to defaults" button in the settings footer clears it. The default configuration is defined in `DEFAULT_SETTINGS` in `App.jsx` and reflects the author's actual commute setup.

## Why the MTA Bus SIRI endpoint has an 8-second timeout

The MTA Bus Time SIRI API (`bustime.mta.info`) can hang indefinitely on weekends or during off-peak hours. Without a timeout, the card would show a loading spinner forever. An 8-second `AbortSignal.timeout` causes the fetch to abort and return `{ timeout: true }` in the response. The card then shows "Feed timed out — try again shortly" in orange rather than silently showing "No upcoming buses" (which would be misleading — the user can't tell if there are no buses or if the feed failed). There is no schedule fallback for MTA Bus since the SIRI API is the only data source.

## Why NJT GTFS refreshes every 7 days instead of 24 hours

NJT publishes GTFS static data updates sporadically — not on a daily schedule. Refreshing every 24 hours was wasteful (downloading 31MB of identical data) and could cause unnecessary disruption if the NJT API was temporarily unavailable. 7 days is a reasonable cadence that catches most schedule changes. The `/api/bus/gtfs-status` endpoint shows cache age and a `stale: true` flag if it's been over 7 days, making it easy to monitor.

## Why the NYC Ferry GTFS URL changed

The original URL (`https://nycferry.connexionz.net/rtt/public/resource/gtfs.zip`) was returning 403. The correct URL is `http://nycferry.connexionz.net/rtt/public/utility/gtfs.aspx` (from the official Transitland feed registry). Additionally, the realtime feed always sends an empty `routeId` field — the route must be resolved by looking up the `tripId` in the static GTFS `trips.txt`. The server now builds a `tripId → { routeId, headsign }` map at startup.

## Why the MTA station routes cache is a file instead of memory

The station-to-route mapping is built by parsing the full MTA subway GTFS static data (stop_times.txt has ~500k rows). This takes several seconds and shouldn't happen on every server restart. Storing it in `.cache/mta_station_routes.json` means it's built once and reused. The server auto-builds it on startup if the file is missing (e.g. after a fresh clone). The `server/build_station_routes.mjs` script can also be run manually.

## Why the MTA subway GTFS zip is cached and shared

Both `loadMtaStations()` (station search) and `build_station_routes.mjs` (routes cache builder) need the same MTA subway GTFS zip. Originally, `loadMtaStations` downloaded a fresh copy on every server restart while the routes cache was built from a separate download. If the GTFS data changed between the two downloads, station IDs could differ and the routes lookup would silently return empty lines.

The fix: both functions share a single cached zip at `.cache/gtfs_subway.zip`, refreshed every 7 days. This guarantees the station IDs in the search results always match the keys in `mta_station_routes.json`. It also avoids a redundant 5MB download on every server restart.

## Why PATH matching changed from stop ID to route+direction

The PATH GTFS-RT community feed only reports each train's next stop — not the full trip sequence. Filtering by `stopId === '26729'` (Hoboken) would only catch trains still sitting at Hoboken, missing all trains already en route. The fix matches on `routeId + directionId` only and takes the earliest reported stop time as the ETA. This correctly captures all trains heading in the right direction regardless of where they currently are.


## Why Lightsail VPS instead of App Runner or Amplify

AWS Amplify is designed for static frontends + serverless (Lambda) backends. This app is a **persistent Node.js server** — it holds the NJT auth token in memory (20h TTL), caches GTFS data in memory and on disk, and maintains in-memory caches for PATH, ferry, and MTA feeds. Lambda functions are stateless and spin down between requests, which would cause constant re-authentication and cache misses.

AWS App Runner is closer but lacks persistent disk — the `.cache/gtfs.zip` would be lost on every deploy, forcing a 31MB re-download each time.

A Lightsail VPS ($5/mo, 2GB RAM) gives a persistent process, persistent disk, predictable flat billing, and the ability to host multiple apps on the same instance later. GitHub Actions handles auto-deploy via SSH on every push to `master`.

## Why 2GB RAM on Lightsail (not 1GB)

The initial deployment used a 1GB RAM instance. This caused SSH connections to hang during deploys and the service to fail continuously. The root cause: `npm run build` (Vite + React) requires significant memory, and with only 1GB the build process would exhaust RAM, causing the OS to kill processes and leaving the server in a broken state.

Upgrading to the 2GB plan ($10/mo) resolved all stability issues immediately. For a Node.js app that also runs `npm run build` on the server during deploys, 2GB is the practical minimum.

## Why the production catch-all must come last

In production mode, Express serves the React SPA via a `*path` catch-all route that returns `index.html` for any unmatched path. Any API endpoint registered **after** this catch-all will never be reached — the catch-all intercepts the request first and returns HTML.

The `/api/bus/gtfs-status` endpoint was originally registered after `app.listen()`, which placed it after the catch-all in Express's route stack. It returned HTML instead of JSON in production. The fix: register all API endpoints before the production static-serving block.

**Rule:** all `app.get('/api/...')` routes must be defined before `app.use(express.static(...))` and the `*path` catch-all.

## Why Express 5 requires named wildcards

Express 5 upgraded its underlying `path-to-regexp` library to v8, which no longer accepts unnamed wildcards (`*`). Routes like `app.get('/*', ...)` throw a `TypeError` at startup.

The fix is to name the wildcard: `app.get('/*path', ...)`. The captured value is then available as `req.params.path` instead of `req.params[0]`. In this app, the production proxy routes used `req.path` directly (not `req.params`), so only the route definition needed updating — no handler logic changed.

This bug only manifested in production because in dev, Vite's proxy intercepts `/api/panynj/*` and `/api/nws/*` before Express ever sees them.

## Why doc-only pushes skip the deploy workflow

The GitHub Actions deploy workflow runs `npm ci`, `npm run build`, and restarts pm2 on every push. For documentation-only changes (`.md` files, `icon-drafts.html`), this is wasteful — it takes 2-3 minutes and restarts the live server unnecessarily.

The workflow uses `paths-ignore` to skip deploys when only doc files change. Code changes (`src/`, `server/`, `package.json`, etc.) still trigger a full deploy.
